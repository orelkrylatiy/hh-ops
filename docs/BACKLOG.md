# Бэклог hh-ops

Здесь фиксируются открытые проблемы интеграции. Пункты ниже документируют найденные риски; реализация пока **не менялась**.

## [ ] HH-VOICE-01 — Выбранное резюме не определяет профиль запроса и персональный стиль

**Тип:** bug / integration. **Статус:** open.

**Наблюдение:** `_build_cover_letter_context()` готовит факты выбранного резюме, но `FrameworkWriter.application()` не принимает и не передаёт его профиль и `VoiceProfile`. Аналогично `FrameworkWriter.chat_reply()` не передаёт эти параметры. `build_application_request()` и `build_chat_reply_request()` используют `profile="frontend-react"` и `DEFAULT_CHAT_VOICE` с описанием «Фронтенд-инженер...» и пустым `examples=[]`.

**Воздействие:** факты резюме **не подменяются** на frontend-факты автоматически; они передаются отдельно в `source_context` / `resume_context`. Однако метаданные и стилистические инструкции не связаны с выбранным резюме и утверждённым авторским голосом. В частности, другое резюме (например, AI Engineer) получает те же frontend-ориентированные инструкции.

**Где смотреть:** `src/hh_applicant_tool/operations/_apply_vacancies_apply_flow.py::_build_cover_letter`, `automation/reply_worker.py::generate_reply`, `communication/live.py`, `communication/adapter.py`.

**Предлагаемое исправление:**
- Передавать выбранный профиль/alias до `CommunicationRequest.profile` без жёсткого frontend-default на рабочем пути.
- Передавать явно отдельный персональный VoiceProfile (не путать профессиональные факты со стилем); различать жанры `application` и `chat_reply`.
- Добавить тесты для frontend- и AI-резюме и проверить, что факты, профиль и стиль не смешиваются между аккаунтами/откликами.

**Готово, когда:** интеграционные тесты подтверждают выбранный профиль и ожидаемый VoiceProfile для каждого резюме; факты берутся только из выбранного резюме; текущие ограничения отправки и проверки сообщений не регрессируют.

## [ ] HH-CONTEXT-02 — Потенциальная потеря ключевых фактов при обрезке контекста до 3500 символов

**Тип:** bug / quality risk. **Статус:** open.

**Наблюдение:** hh-ops собирает до 4000 символов описания вакансии и до 4000 символов анализа резюме (плюс прочие поля), затем упаковывает их в `source_context`. В `humanizer-framework/src/humanizer_framework/prompting.py::build_prompt` сериализованный `request.context` обрезается `_clip_text(..., 3500)` с сохранением начала и конца. При длинном входе часть середины выпадает, возможна потеря требований вакансии или релевантных фактов.

**Важно:** сам бюджет 3500 символов **не считается ошибкой**. Риск — **неосознанное, смыслово-слепое отсечение** данных без явного подтверждения, что важные факты сохранены. Кроме того, обрезка уже сериализованного JSON может нарушить его структуру.

**Где смотреть:** `src/hh_applicant_tool/operations/_apply_vacancies_ai.py::_build_cover_letter_context`, `communication/adapter.py::build_application_request`, `humanizer-framework/src/humanizer_framework/prompting.py`.

**Предлагаемое исправление:**
- Перед генерацией составлять компактный структурированный набор требований вакансии и подтверждённых фактов выбранного резюме.
- Сохранять критичные поля целиком или явно обнаруживать и протоколировать отсечение (без публикации резюме и персональных данных в логах).
- Написать тест с длинной вакансией и несколькими достижениями в середине резюме; проверять, что модель получает нужные данные. Не повышать глобальный лимит без отдельной оценки затрат и качества.

**Готово, когда:** длинные исходные данные не вызывают молчаливой потери обязательных фактов в подготовленном запросе, а сокращение контекста контролируемо и покрыто тестами.

## [x] HH-DAILY-03 — Сбой откликов останавливал ответы работодателям

**Тип:** bug / orchestration. **Статус:** fixed.

**Проблема:** `scripts/daily.sh` выполнял `apply.sh` перед `reply.sh` при `set -e`. Ненулевой код откликов (например, ошибка LLM или email после уже успешных откликов) не позволял запустить независимый этап ответов работодателям.

**Исправление:** отдельный учёт результата каждого этапа через `run_stage`. Неудача `boost` или `apply` не блокирует последующие запланированные этапы, но итоговый код завершения остаётся ненулевым. Добавлены офлайн-тесты с подменёнными скриптами: реальные операции hh.ru не выполняются.

**Проверить в runtime:** запуск с рабочими конфигурациями и журнал `HH_DAILY_STAGE` / `HH_DAILY_RESULT`.

## [ ] HH-CAPTCHA-04 — Зависимость от запасного CAPTCHA API и отсутствие отдельного preflight

**Тип:** integration / operational safety. **Статус:** open.

**Наблюдение:** обработчик в `apply_vacancies.py::_solve_captcha_async` создаёт клиент `get_captcha_ai()` до других действий. В `authorize.py::_solve_captcha_with_ai` недоступность клиента останавливает автоматическую ветку. Отдельного независимого preflight или надёжного канала эскалации на ручное подтверждение в общем цикле нет.

**Безопасный объём исправления:** проверять нужные зависимости и настройки до live-прохода, выдавать понятную диагностику, фиксировать причину остановки и передавать CAPTCHA на ручную проверку пользователю. Не продолжать отклики без действительной авторизации и подтверждения сайта.

## [ ] HH-DAILY-05 — Область действия `--profile` при `--with-boost`

**Тип:** bug / scope. **Статус:** open.

**Наблюдение:** `daily.sh --profile X --with-boost` запускает `all-profiles.sh boost --live` для всех профилей из `.profiles`, а отклики/ответы — только для X. Исправить до использования сочетания этих флагов в многоаккаунтном режиме, учитывая блокировки аккаунтов.
